C Consistency

Every node gives the same, up-to-date answer — nobody sees stale or conflicting data.

A Availability

Every request gets some answer right away — the system never just goes silent.

P Partition

Part of the network loses contact with another part — a cable fails, a router drops packets. Nobody chooses this; it's just something that can happen.

New here? Start with the basics ▾

What you're looking at: the building in the middle is a client — think of it as your phone or browser, making a request. The three buildings around it are nodes: separate servers that each keep their own copy of the same data (a replica), so the system keeps working even if one of them goes down. Each cart riding the tracks is one request, heading out and coming back with an answer.

What CAP theorem actually says: when part of the network can't reach another part (a partition — the "P" card above), the system has to make a choice for the requests stuck on the wrong side of the gap: make them wait for a guaranteed-correct answer (Consistency), or answer them right away with whatever data is already on hand, even if it's a little out of date (Availability). You can't have perfect versions of both at once — but only for the requests actually caught in the gap, and only while the partition lasts.

What do real systems actually do about this? ▾

The two buttons you clicked ("Wait for it" / "Answer anyway") are simplified stand-ins for real engineering techniques. Here's what's actually behind each one:

Favoring Consistency ("Wait for it")

  • Quorum reads & writes — require agreement from a majority of replicas (not just one) before confirming anything, so a lone, out-of-sync node can never answer on its own.
  • A single elected leader, kept in sync by a consensus protocol — route all writes through one leader, and use an algorithm like Raft (used by etcd) or the Zab protocol (used by Apache ZooKeeper) to safely re-elect a new leader if the old one disappears, without ever letting two leaders exist at once.
  • Distributed locks — grab a lock from a majority of nodes before changing shared state, so a cut-off minority literally cannot also make changes.
  • Just refuse the request — exactly what you saw: queue it, time it out, or return an error rather than guess. Blunt, but never wrong.

Favoring Availability ("Answer anyway")

  • Sloppy quorum + hinted handoff — if the node that's supposed to hold some data is unreachable, a different reachable node temporarily accepts the write on its behalf (with a "hint" about where it really belongs), then forwards it once the original node comes back. This is literally how Amazon's Dynamo — the design behind Cassandra and DynamoDB — stays writable during a partition.
  • Conflict resolution, once reconnected — two nodes now disagree, so something has to decide the "true" answer:
    • Last-write-wins — keep whichever version has the newest timestamp. Simple, but can silently throw away a real update.
    • Vector clocks — tag each version with which node changed it and when, so the system can tell "this came after that" apart from "these two changed independently and now conflict."
    • CRDTs (Conflict-free Replicated Data Types) — data structures specifically designed so merging two divergent copies happens automatically and always lands on the same sensible answer, with nothing left to resolve by hand.
    • App-level merging — Amazon's own shopping cart is the classic example: instead of picking one version of your cart and discarding the other, Dynamo merges the two, which is why a deleted item can occasionally reappear.
  • Anti-entropy — a background process that compares replicas (often using a Merkle tree, so it only has to compare short summaries instead of every record) and quietly repairs whatever fell out of sync.

Detecting the partition in the first place

  • Failure detection is local, not global — a node simply decides "my peer stopped responding" from its own point of view. There's no referee announcing "a partition has begun," which is exactly why this simulation never shows one global switch.
  • Gossip protocols — nodes periodically swap what they know about each other's health with a random peer, so news of a failure (or a recovery) spreads through the cluster without a central coordinator.

One more thing real systems do that this simulation simplifies away: the choice usually isn't made once for the whole system. Cassandra and DynamoDB, for example, let you pick Consistency or Availability per request — critical operations can wait for a quorum while less critical ones answer immediately, all in the same application.

For the curious: full sources & precise definitions

Everything above is simplified for learning. Here's what it's based on, with the more precise (and more technical) definitions:

  • Brewer, "Towards Robust Distributed Systems" (PODC 2000 keynote) — origin of the conjecture, presented as a rule of thumb, not a proof.
  • Gilbert & Lynch, "Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services" (ACM SIGACT News, 2002) — the formal proof; "consistency" here means atomic/linearizable consistency, not ACID consistency.
  • Brewer, "CAP Twelve Years Later: How the 'Rules' Have Changed" (IEEE Computer, 2012) — partition tolerance isn't optional for a real networked system; the C-vs-A choice happens per-operation, during an actual partition; recovery includes compensating for mistakes (his ATM example, reused below).
  • Abadi, "Consistency Tradeoffs in Modern Distributed Database System Design" (PACELC, IEEE Computer, 2012) — extends CAP with the latency/consistency tradeoff that exists even without a partition.
  • Kleppmann, "A Critique of the CAP Theorem" (arXiv:1509.05393, 2015) — "It is misleading to say that an algorithm 'provides partition tolerance'... better to say an algorithm 'assumes that partitions may occur.'" This simulation follows that framing: partitioning is never a global switch you flip on a whole system, it's something that happens to a subset of nodes.
  • DeCandia et al., "Dynamo: Amazon's Highly Available Key-value Store" (ACM SOSP, 2007) — source for the "favoring Availability" techniques above: sloppy quorum, hinted handoff, vector clocks, Merkle-tree anti-entropy, gossip-based failure detection, and the shopping-cart merge example, all taken directly from Table 1 and Sections 4.4–4.8 of the paper.
